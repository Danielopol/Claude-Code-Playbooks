## What This Does

A client-side implementation guide for Android's Restore Credentials feature, from Google's own `android/skills` repository, built around the Credential Manager API (`androidx.credentials`). It implements the two-tier restoration architecture correctly: a primary background tier that fires from `BackupAgent.onRestoreFinished()` during device setup (invisible to the user, enabling background sync and notification delivery before the app is ever opened) and a secondary foreground tier in the launcher `Activity` that catches failovers when background restoration didn't complete or `allowBackup` is disabled — implementing only the tier that actually applies based on the manifest's `allowBackup` value, and never changing that value to enable the feature.

The scope is deliberately narrow and explicit: this is Android client-side integration only. The playbook works through creating a restore key (with the required fallback — retry `createCredential` with `isCloudBackupEnabled = false` if `E2eeUnavailableException` fires because the device lacks a screen lock or end-to-end encryption), signing in with a restore key on a new device, and deleting it correctly on sign-out with `clearCredentialState`. It closes with backend guidelines presented to the developer as a reminder rather than implemented directly — distinguishing restore credentials from user-visible passkeys in storage, preventing orphaned keys after an uninstall, and handling multi-device and remote session-invalidation cases server-side.

## Tips & Best Practices

- Always implement the `E2eeUnavailableException` fallback — a device without a screen lock or end-to-end backup encryption will throw it on `createCredential` with `isCloudBackupEnabled: true`, and skipping the retry silently leaves those users without a restore key at all.
- Restore keys are per-package-name; an organization with multiple apps sharing user accounts needs a separate restore key generated for each app.
- Distinguish restore credentials from user-created passkeys in your backend storage from day one — they use the same underlying WebAuthn mechanism, but restore credentials must stay hidden from any user-facing passkey-management UI.

## Limitations

- Client-side only by design — the matching server-side cryptographic validation and relying-party setup is explicitly out of scope and must be implemented separately, following the backend guidelines this playbook hands off.
- Requires Android 9 (API 28)+, Google Play services core 24220000+, and `androidx.credentials` 1.5.0+; older devices fall back to the app's normal sign-in flow.
- `onRestoreFinished()` (not `onRestore()`) is the callback that reliably fires for any kind of backup restore — using the wrong callback silently breaks the background tier without an obvious error.
