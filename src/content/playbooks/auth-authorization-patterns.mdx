## What This Does

A compact, high-signal checklist of the auth patterns that matter most, split cleanly along the distinction that trips up the most implementations: authentication (proving *who* a user is) versus authorization (deciding *what* they may do). It states each rule with the specific attack or failure it prevents, so the guidance transfers to any stack rather than being a copy-paste snippet — why password hashes must be deliberately slow (brute-forcing leaked dumps), why access tokens stay short-lived and refresh tokens stay out of `localStorage` (XSS theft), why authorization gets re-checked on every request rather than trusted from a one-time login, and why OAuth2 user flows need Authorization Code with PKCE (code interception on public clients).

It covers the full surface a typical login system touches: password hashing (bcrypt/argon2, never MD5/SHA-1), short-lived JWTs paired with securely-stored refresh tokens, MFA for sensitive operations, RBAC/ABAC enforced at the service layer rather than hidden in the UI, least privilege for every role and token, the four JWT/OIDC claims to always validate (`iss`, `aud`, `exp`, `nonce`), and session hygiene (regenerate the session ID on login to block fixation; set `HttpOnly` and `Secure` on cookies). A final quick-review checklist makes it usable as a pre-ship or PR-review gate.

## Tips & Best Practices

- Treat "check authorization on every request" as non-negotiable — the most common real-world authorization bug is a system that authenticates correctly at login and then assumes that token is a blanket permission for every subsequent action.
- Keep access tokens genuinely short-lived (15–60 minutes) and lean on refresh tokens for longevity — a long-lived access token is the single change that most widens the blast radius of any token leak.
- Never store a token your frontend JavaScript can read if you can avoid it — an `HttpOnly` cookie survives an XSS incident that would hand `localStorage` contents straight to the attacker.

## Limitations

- A patterns checklist, not a drop-in implementation — the correct library and exact configuration depend on your language and framework, and the whole point of rule one is to use a vetted library rather than code these primitives yourself.
- Covers the common web/app auth surface (passwords, JWT, OAuth2/OIDC, sessions, RBAC/ABAC); specialized needs like passwordless/WebAuthn, mTLS, or hardware-backed keys have their own additional considerations beyond this list.
- Security guidance evolves — treat this as a strong default baseline and still check current OWASP and your identity provider's own recommendations for anything high-stakes.
