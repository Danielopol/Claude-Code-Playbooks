## What This Does

A dense, checkable reference for web typography — not a style guide of opinions, but a set of specific rules each tied to a concrete CSS property and a nameable failure mode. It covers font loading correctly (real weights instead of browser-synthesized ones, `.woff2` over other formats, CSS properties like `font-weight: 650` preferred over raw `font-variation-settings` tags so a non-variable fallback still works), a semantic type scale with heading sizes that descend by level so a child heading can never visually overpower its parent, line-height and letter-spacing rules by content role, and the four `text-wrap`/`overflow-wrap`/`white-space` declarations each doing one specific job — `balance` for headings, `pretty` to stop an orphaned word on a description's last line, `nowrap` for labels that shouldn't break.

It closes with two things that make it more than a reference: a table of twelve specific, common mistakes mapped directly to their fixes (a thin font weight on 14px UI text, `leading-none` on a three-line card description, justified text in application UI), and a structured review-report format with severity ratings (HIGH blocks, MEDIUM breaks the type system, LOW is polish), an explicit verification method for reviewing with or without a browser, and a rule against approving coverage that wasn't actually inspected. It also scopes itself honestly against neighboring concerns — word choice belongs to a writing skill, semantic heading structure to an accessibility skill, RTL layout to a layout skill, contrast measurement to a color skill — this one owns specifically how text renders, wraps, and behaves.

## Tips & Best Practices

- Always review typography by looking at the rendered page, not just the code — widows, orphans, and truncation only become visible at real content lengths, and code alone won't reveal them.
- Apply `-webkit-font-smoothing: antialiased` once on the root layout, never per-component — a per-component approach produces inconsistent text weight across the page on macOS.
- When choosing between the two 16px-mobile-input fixes (sizing up the input vs. `transform: scale()`), ask which visual tradeoff the design actually wants rather than defaulting to one — they look meaningfully different on small screens.

## Limitations

- Deliberately scoped to typography rendering and behavior — word choice, semantic heading structure, RTL/logical-property layout, and contrast measurement are explicitly out of scope and belong to neighboring accessibility, writing, layout, and color skills.
- The review-report format assumes a codebase where typography lives in inspectable CSS/Tailwind classes; a heavily inline-styled or CSS-in-JS-obfuscated codebase may need more manual tracing to locate each finding's file:line.
- Recommendations assume a standard web rendering context — a canvas-rendered or WebGL text layer won't benefit from CSS-level fixes like `text-wrap` or `font-variant-numeric`.
