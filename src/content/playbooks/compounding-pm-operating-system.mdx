## What This Does

Most PM frameworks are static — the same opportunity template, the same prioritization matrix, every single time, with no memory of what you tried before or whether it worked. This is different: a `pm-profile.yaml` file that captures your actual frameworks, vocabulary, and decision history, and gets updated after every product cycle with real predictions-vs-actuals data.

The mechanism is simple but the effect compounds: by cycle 5, the system is suggesting activation thresholds calibrated from your last four projects instead of generic benchmarks. By cycle 10, it knows your estimation bias and corrects for it automatically, and flags when a new opportunity resembles a past failure before you commit resources to repeating it.

## The Full Loop

```
Observe → Opportunity → Solution → Spec → Review → Measure → Compound
   ↑                                                              │
   └──────────────────── learnings feed back ─────────────────────┘
```

| Step | What it produces |
|------|--------------------|
| Opportunity | A structured, evaluated opportunity doc — signal classified, problem framed as a How Might We, prioritized on impact/risk |
| Solution | Multiple solution approaches, classified as Differentiator / Must-Match / Neutralizer |
| Spec | Vision narrative, journey map, metrics framework, launch criteria |
| Review | Prioritized findings (P1 blocking / P2 should-fix / P3 nice-to-have) |
| Measure | Explicit, falsifiable predictions — not vague directional hopes |
| **Compound** | Predictions compared to actuals, profile updated — **the step that makes everything else worth doing** |

## What Gets Personalized

| Profile field | Adapts |
|-----------------|--------|
| Frameworks (opportunity evaluation, solution classification, metrics hierarchy) | How each step structures its output |
| Vocabulary | Whether you call it a "north star," an "outcome metric," or a "KPI" |
| Thresholds | Pre-filled targets calibrated from your actual project history |
| Project patterns | Surfaced automatically when a new opportunity resembles a past one |
| Decision log | Surfaced when a similar trade-off comes up again |

## Tips & Best Practices

- **Never skip Compound.** It's explicitly framed in the source material as "the most important step" — everything before it is just PM templates with a chatbot attached. The compounding only happens if predictions get checked against reality and the profile gets updated.
- **Make predictions specific and falsifiable.** "Adoption will improve" isn't a prediction the system can learn from. "35% activation within 7 days" is — it has a number that can be right or wrong.
- **Classify failures by type, not just outcome.** The template distinguishes strategy failure (wrong market), opportunity failure (right market, wrong problem), prioritization failure (right problem, wrong solution), execution failure, and measurement failure — because the fix is different for each one.
- **Let it surface past patterns before you ask.** When a new opportunity resembles something already in `project_patterns`, the system should say so proactively — that's the whole value of the memory existing.
- **Start minimal if you're not sure.** A skeleton profile that fills in through actual usage beats an elaborate upfront setup you have to guess at before you've run a single cycle.

## Limitations

- The compounding value is genuinely cumulative — cycle 1 looks like any other PM template, and the differentiation only shows up after several real cycles have fed the profile
- Works best with a git-tracked project where `pm-profile.yaml` and the `docs/` output persist between sessions — it's designed around a durable file, not a one-off conversation
- For a team, a shared `team-profile.yaml` layer requires deliberate promotion of individual learnings — insights don't automatically become team knowledge without an explicit sharing step
- This playbook condenses the operating system's core loop and compounding mechanism; the source repository also ships dedicated judgment-training exercises (teardown practice, reaction simulation, bias checks) and standalone strategy/growth commands (segmentation, competitive differentiation, North Star metric design) worth exploring directly in the source if you want the full toolkit
