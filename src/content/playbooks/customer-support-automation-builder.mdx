## What This Does

Instead of a fixed integration for one platform, this walks Claude through building a support automation system tailored to whatever you actually run — Zendesk, Intercom, HelpScout, Freshdesk, or Front for tickets; Stripe, Chargebee, Paddle, or Braintree for billing; Postgres, MySQL, or MongoDB for customer lookups. The output is real, working TypeScript you keep and extend, not a one-off script.

The generated system auto-triages every open ticket by urgency, gathers full customer context (billing status, subscription, ticket history) before drafting anything, and never sends a reply without your explicit approval.

## Tips & Best Practices

- **Discovery comes before code.** The build starts by asking what your actual stack is — never assume Zendesk-and-Stripe. Answer honestly even if your setup is unusual; the scripts adapt to whatever API you point at.
- **Database access is read-only by construction, not convention.** The `query-db.ts` script only permits `SELECT`, `WITH`, `SHOW`, and `EXPLAIN` at the code level — a bad prompt can't accidentally turn into a write.
- **Every script outputs structured JSON.** That's what lets Claude parse results and chain scripts together in a workflow, rather than scraping console output.
- **Approval is required before every send — no exceptions.** The whole system is built around "suggest, don't decide": Claude drafts, you approve, then it sends. This holds even after the system has proven reliable.
- **Use idempotency keys on refunds.** A retried refund request should never double-refund — Stripe and most processors support this natively.
- **Test with `check-setup.ts` before anything else.** It validates every required environment variable is present, catching missing credentials before they fail mid-workflow.

## Real-World Reference Point

The author built this pattern for [Lex](https://lex.page)'s support operation: 15 scripts across HelpScout, Stripe, and Postgres, 6 response templates, keyword-based automatic triage, and unified customer context — handling roughly 80% of support tasks through yes/no approvals.

## Limitations

- Best suited for teams with API access to their tools and someone comfortable running TypeScript scripts and managing credentials — not a no-code solution
- Initial build takes 30–60 minutes for a basic setup; more platforms or a more complex stack takes longer
- Assumes 10–100 tickets/day volume; enterprise support software with dedicated automation tooling may already cover this ground
- The generated scripts are a starting point you're expected to extend — new scenarios need new templates, new repetitive operations need new scripts
