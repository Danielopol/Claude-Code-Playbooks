## What This Does

A practical guide to the embedding layer of a RAG or semantic-search system, covering the decisions that actually move retrieval quality: which model to pick (a comparison table across OpenAI, Voyage, BGE, MiniLM, and E5 with dimensions, token limits, and best-fit use cases), the model-specific query/document prefixes that several open models were trained with and silently underperform without (BGE's query prefix, E5's `query:`/`passage:` split), Matryoshka dimension reduction to cut storage and speed up search on the `text-embedding-3-*` models, and four chunking strategies (token, sentence, markdown-section, and recursive character splitting) chosen to preserve semantic boundaries rather than cut mid-thought.

Crucially, it closes the loop with a retrieval-quality evaluation harness — precision@k, recall@k, MRR, and nDCG@k computed against a labeled query→relevant-docs set — so an embedding or chunking change gets measured instead of guessed at, plus the normalization and batching practices that keep cosine similarity correct and API costs down. The code is runnable Python (OpenAI, sentence-transformers, tiktoken, nltk), and the Do's/Don'ts call out the traps that corrupt a vector index silently: mixing embedding models in one index, ignoring token-limit truncation, and skipping preprocessing.

## Tips & Best Practices

- Apply the model's required query/document prefix before anything else — a BGE or E5 model used without it is the most common self-inflicted RAG retrieval problem, and no amount of chunking tuning compensates for it.
- Never mix embedding models within a single index; their vector spaces are incompatible and the similarity scores become meaningless, usually without any error to warn you.
- Measure every embedding or chunking change against a labeled set with the included metrics — "it feels better" is exactly how teams ship a change that quietly lowered recall.

## Limitations

- The model comparison table is a point-in-time snapshot of a fast-moving field — treat dimensions and token limits as current-ish starting points and confirm against each provider's live docs before committing an index.
- Retrieval-quality metrics require a labeled query→relevant-docs set to compute; if you have no labeled data yet, building that set is the real first step, and the harness only pays off once it exists.
- Covers the embedding/retrieval layer specifically — the generation side of RAG (prompt construction, reranking, answer grounding) is a separate concern this playbook doesn't address.
