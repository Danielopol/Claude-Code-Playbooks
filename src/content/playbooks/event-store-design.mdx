## What This Does

A design-and-implementation guide for the event store at the heart of an event-sourced system. It starts from the model that makes event sourcing work — one append-only, immutable, per-aggregate stream with both per-stream and global ordering — and the five requirements any real event store has to meet (append-only, ordered, versioned, subscribable, idempotent). A technology comparison table lays out when EventStoreDB, PostgreSQL, Kafka, DynamoDB, or Marten is the right backend and what each gives up.

The core of the playbook is a complete, correct PostgreSQL implementation: an `events` table with a `global_position` sequence and the `UNIQUE(stream_id, version)` constraint that enforces optimistic concurrency (a conflicting concurrent write fails and forces a re-read rather than corrupting the stream), plus `snapshots` and `subscription_checkpoints` tables and the indexes each query pattern needs. It pairs that with an immutable `Event` record, the four core operations (append with expected-version, read-stream for replay, read-all for projections, subscribe for live consumers), snapshotting to bound replay cost, and the DynamoDB conditional-write equivalent — then closes with the do's and don'ts that keep an event log trustworthy (never mutate events, keep payloads small, never skip optimistic concurrency, include correlation/causation IDs for tracing).

## Tips & Best Practices

- Treat the `UNIQUE(stream_id, version)` constraint as non-negotiable — it is the entire optimistic-concurrency mechanism; dropping it to "simplify" the schema reintroduces the silent stream-corruption bug event sourcing exists to prevent.
- Version your events from day one and keep correlation/causation IDs in metadata — both are nearly impossible to retrofit cleanly once you have production history, and both are what make schema evolution and cross-service tracing tractable later.
- Snapshot long streams so aggregate reconstruction doesn't replay from event 1 on every load — but keep snapshots as a derived optimization, never the source of truth.

## Limitations

- This is the persistence layer only — projections/read models, command handling, and schema/upcasting strategies for evolving event shapes are adjacent concerns the playbook points at but doesn't fully implement.
- The PostgreSQL schema is a solid general-purpose starting point, not a tuned high-throughput configuration; very high write volumes may need partitioning, archival tiers, or a purpose-built store like EventStoreDB or Kafka.
- Event sourcing is a significant architectural commitment with real operational cost — this playbook assumes that decision is already made and doesn't argue whether a given system should be event-sourced at all.
