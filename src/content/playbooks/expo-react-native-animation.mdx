## What This Does

Turns "add an animation" into a disciplined build sequence instead of an improvised implementation. It starts with a hard gate — should this even animate, given how often it fires (a tab switch happening 100+ times a day should never animate; a rare celebration state is where the delight budget belongs) — then walks through naming the animation's actual purpose, picking the cheapest tool that fits from a real decision table (a native tab bar over a hand-rolled one, a native sheet over a custom modal, a shared value only when the interaction is genuinely continuous or gesture-driven), and choosing concrete spring or easing values instead of approximated ones.

The core of the discipline is keeping motion off the JS thread — the specific mobile failure mode that makes an animation look fine in dev and drop to 20fps in production: no state updates inside a gesture handler, no per-frame cross-thread scheduling, no reading or writing a shared value during render. It closes with press-not-hover redesign rules (mobile has no hover state), sparing and well-timed haptics, reduced-motion handling that ships with the animation rather than after it, and a hard rule that feel is only judged on a release build on the slowest supported device — nothing else counts as verified.

## Tips & Best Practices

- Be opinionated and brief. When the honest answer is "this shouldn't animate" or "this needs a real device before I can tell you if it's right," give that answer rather than hedging.
- The frequency gate is the highest-leverage check in the whole sequence — most janky, over-animated mobile UIs trace back to skipping it and animating something that fires dozens of times a session.
- When a review flags stutter, check the JS-thread rules before touching timing values — a state update hiding inside a gesture handler causes far more visible jank than a slightly-off spring config.

## Limitations

- Specific to React Native and Expo — the underlying principles (interruptibility, velocity handoff, keeping animation off the main thread) generalize, but the concrete APIs here don't transfer directly to native iOS/Android or the web.
- Assumes a project already has, or can add, a real UI-thread animation and gesture library — without one, several of the tool-selection recommendations need different entries.
- Feel verification genuinely requires physical devices across a performance range — a review done entirely in a simulator or on a single high-end device will miss exactly the problems this discipline exists to catch.
