## What This Does

A systematic seven-phase process for building non-trivial features: discovery, parallel codebase exploration, clarifying questions (that block until answered), multi-approach architecture design with a recommendation, implementation only after explicit approval, three-angle quality review, and a final summary. Designed for features that touch multiple files or require real architectural decisions — not one-line fixes.

## The Seven Phases

1. **Discovery** — clarify what's actually being built and confirm understanding
2. **Codebase Exploration** — 2–3 parallel agents trace similar features, architecture, and patterns; every file they identify gets read, not just summarized
3. **Clarifying Questions** — every ambiguity, edge case, and integration question surfaces here, before any design work starts. This phase is explicitly not skippable.
4. **Architecture Design** — 2–3 competing approaches (minimal-change, clean-architecture, pragmatic-balance) with trade-offs and a stated recommendation; you pick
5. **Implementation** — starts only after explicit approval, following the chosen architecture and existing conventions
6. **Quality Review** — three parallel review agents check simplicity/DRY, bugs/correctness, and convention adherence
7. **Summary** — what was built, key decisions, files touched, suggested next steps

---

## Tips & Best Practices

- **Answer the clarifying questions thoughtfully** — Phase 3 exists specifically to prevent the rework that comes from unstated assumptions
- **Trust the architecture recommendation** — it's built from actual exploration of your codebase, not a generic best-practice guess
- **"Whatever you think is best" still needs your confirmation** — if you say this, you'll get a specific recommendation and a request to confirm it, not silent autonomy
- **Be specific in the initial request** — more detail up front means fewer clarifying-question rounds later

## When to Use This

**Use it for:** new features touching multiple files, features needing architectural decisions, complex integrations, requirements that are somewhat unclear.

**Skip it for:** single-line fixes, trivial changes, well-defined simple tasks, urgent hotfixes — the structure adds overhead these don't need.

## Limitations

- Exploration on a large codebase takes real time — that's the cost of the thoroughness, not a bug
- Requires an existing codebase with patterns to learn from; less useful for pure greenfield work
