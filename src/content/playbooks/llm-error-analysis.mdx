## What This Does

The foundational error-analysis methodology from Hamel Husain's eval work — the step that should come before any evaluator, judge, or dashboard gets built. Rather than borrowing generic quality metrics ("helpfulness", "hallucination", "coherence") that look rigorous and miss what a product actually gets wrong, it has you read ~100 real (or synthetic) traces, judge each pass/fail, and note the **first** thing that went wrong (errors cascade, so fixing the root cause makes the downstream symptoms disappear). Failure categories are allowed to emerge from what you observe instead of being imposed from a pre-defined list, which is the difference between evaluators that catch real problems and ones that score well on paper.

The seven steps run from trace collection (full traces, with diversity via embedding clustering) through reading-and-noting, grouping into 5–10 distinct and actionable categories (with explicit split-vs-group heuristics and cautious LLM-assisted clustering only after a human has reviewed the first batch), binary labeling, and failure-rate computation to prioritize. The step that saves the most wasted effort is the triage: before building any evaluator, check whether a failure just needs an obvious fix — a missing prompt instruction, an unexposed tool, a plain code bug — and do that first, reserving evaluators for failures you'll actually iterate on repeatedly and preferring code-based checks over LLM judges for anything objective. It includes a trace-sampling strategy table and an anti-patterns list, and pairs directly with the companion eval-audit playbook.

## Tips & Best Practices

- Resist the urge to pre-define failure categories — reading traces first and letting categories emerge is the whole method, and starting from a fixed list bakes in confirmation bias that hides your real failures.
- Note only the first thing that went wrong in each trace; chasing every downstream symptom wastes effort on issues that vanish once the root cause is fixed.
- Expect many top failures to need no evaluator at all — a missing prompt instruction or an unexposed tool is a direct fix, and building a judge for it instead is exactly the wasted work this method is designed to prevent.

## Limitations

- It needs a human (ideally a domain expert) in the loop for the first 30–50 traces — this is deliberate, since grounding categories in domain knowledge is the point, but it means the method isn't fully automatable.
- The ~100-trace saturation target scales with system complexity; a simple pipeline saturates sooner and a complex multi-agent one may need more, so treat the number as a heuristic, not a quota.
- It produces grounded failure categories and a fix/evaluator triage — actually writing and validating the evaluators for the failures that warrant them is the next step, covered by the companion eval-audit playbook and judge-writing methodology.
