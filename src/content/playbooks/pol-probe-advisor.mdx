## What This Does

Interactive decision tree for picking the right PoL probe type. Extracts hypothesis + specific risk + timeline + resources, then matches to one of 5 probe flavors with matching tools, success criteria, and disposal plan.

Pairs with `pol-probe` (artifact template) and `problem-statement` (frame the hypothesis first).

```bash

mv ~/Downloads/CLAUDE.md ~/Documents/PolProbeAdvisor/
```

Provide hypothesis, specific risk, timeline, and available resources. Claude recommends the probe type, tools, success criteria, and disposal plan.

## The 5 Probe Flavors

| Type | Core Question | Timeline |
|------|---------------|----------|
| **Feasibility Check** | Can we build this? | 1-2 days |
| **Task-Focused Test** | Can users complete this without friction? | 2-5 days |
| **Narrative Prototype** | Does this workflow earn buy-in? | 1-3 days |
| **Synthetic Data Simulation** | Can we model this without production risk? | 2-4 days |
| **Vibe-Coded PoL Probe** | Will this survive real user contact? | 2-3 days |

## Tips & Best Practices

- **Match method to hypothesis, not tooling.** "I know Figma" ≠ "Figma is right for this risk."
- **Code is last resort.** Most probes don't need it — storytelling, simulation, or specialized tools are cheaper.
- **Define failure before building.** "We'll know it when we see it" = no harsh truth.
- **Set disposal date upfront.** Vibe-Coded probes especially — they look real enough to invite scope creep.
- **One probe, one hypothesis.** Testing 3 things at once = ambiguous results.

---

## Common Pitfalls

- Choosing validation method based on tooling comfort
- Defaulting to code when a Loom + 5 prospects would learn more
- Treating Vibe-Coded probe like production (no disposal plan)
- Testing multiple hypotheses in one probe
- Skipping pre-defined success criteria
