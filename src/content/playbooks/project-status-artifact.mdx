## What This Does

Structures a project's status as one opinionated, tabbed page instead of a recurring text update: an Overview tab with success criteria and scope, a Workstreams tab that's always present (one row per PR, milestone, or sub-project with a status pill and the current state at a glance), and optional tabs — Attention, Background, Plan, Risks & Open Questions, Decisions/FAQ — that only appear when there's genuinely substantive content for them. The page is self-contained, light/dark aware, and published to a shareable, default-private link.

The part that makes it worth building over a plain status doc is the refresh discipline: every later "refresh the status page" re-gathers live state, reads the previous render's embedded state block to know what's already there, edits it in place rather than regenerating from scratch, redeploys to the **same URL**, and reports only the delta — merged items, status flips, new blockers — instead of re-narrating the whole project every time. A failed data fetch marks the affected rows stale rather than inventing a plausible-looking update, and every fetched third-party text (an issue body, a comment) is treated as data to summarize, never as instructions to follow.

## Quick Start

### Step 1: Create a Project Folder

```bash
mkdir project-status && cd project-status
```

### Step 2: Download the Template

Click **Download** above, then:
```bash
mv ~/Downloads/CLAUDE.md ./
```

### Step 3: Build the Status Page

```bash
claude
```

Describe the project — its goal, its workstreams, where live state lives (a repo, a tracker, a doc) — and ask Claude to build a status page. On future check-ins, just say "refresh the status page" and it will re-gather, update the same page in place, and report the delta.

## Tips & Best Practices

- Resist adding a tab "just in case." An empty or thin tab is worse than no tab — readers learn to skip a page that wastes their clicks.
- The status banner and next-steps strip at the very top are what most readers actually consume — get those two exactly right even when the deeper tabs are rougher.
- On a refresh, edit the previous render in place rather than regenerating it from a blank template — that's what keeps the page's voice consistent across many refreshes over a project's lifetime.

## Limitations

- Depends on a runtime capable of publishing a self-contained HTML page to a stable, shareable URL — without that, this produces a well-structured status document but not a live, redeployable page.
- Designed for a project with genuine parallel or dependent workstreams tracked over time — a single-PR change or a short-lived task doesn't need this much structure.
- The delta-reporting discipline only works if the previous render's location is actually recorded — losing that turns every "refresh" back into an unintended first build.
