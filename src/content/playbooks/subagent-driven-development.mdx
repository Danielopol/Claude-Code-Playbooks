## What This Does

A disciplined execution loop for implementation plans with mostly-independent tasks: dispatch a fresh, isolated subagent per task, review that task for spec compliance and code quality before marking it done, run a bounded fix loop when the review finds problems, and close out with one broad review across the whole branch. Fresh context per task means no pollution from earlier tasks' history; a separate reviewer means the same agent isn't grading its own work.

The two ideas that make this hold up under real, long sessions: a **ledger** that records every task completion and every autonomous decision, so a compaction or restart never causes an already-finished task to get re-dispatched — the single most expensive failure this workflow guards against — and a **"rulings, not stalls"** policy that has the agent decide conflicts and ambiguities itself (with the decision logged) rather than pausing to ask, reserving actual stops for only four cases: irreversible operations, security-sensitive actions, side effects outside the workspace, or a plan broken enough that every path forward is a guess.

## Tips & Best Practices

- Treat writing to the ledger as part of completing a task, not an optional afterthought — it's the only thing that survives a compaction, and skipping it defeats the entire point of the workflow.
- Don't skip the task reviewer on "obviously simple" tasks. The review is cheap relative to the cost of a subtly wrong task compounding into three more tasks built on top of it.
- When the fix loop reaches round 4–5, actually switch to a stronger model if one is available — repeating the same approach with the same model rarely breaks whatever pattern caused rounds 1–3 to fail.

## Limitations

- Assumes plan tasks are genuinely independent enough to implement in isolation — tightly coupled tasks fight this model and are better handled by continuous, manual execution instead.
- The fix-loop cap (5 rounds) is a deliberate circuit breaker, not a success guarantee — a task that consistently blows through it usually signals a plan defect, not an implementation problem worth more retries.
- Needs real subagent-dispatch capability (parallel or sequential agent tooling) — without it, the "fresh subagent per task" isolation this approach depends on isn't available.
