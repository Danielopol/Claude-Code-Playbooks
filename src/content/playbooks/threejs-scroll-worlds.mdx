## What This Does

A comprehensive methodology for building 3D scrollytelling experiences correctly — as one persistent Three.js world with one normalized, reversible scroll state driving it, rather than the far more common (and far more broken) pattern of a new renderer or scene per section that visibly teleports between chapters and can't survive a browser back-button or a fast scroll-skip. It starts before any code: writing a "world bible" that defines one reusable visual grammar (scale system, silhouette language, palette progression, material families, light roles, motion grammar) so every visible detail supports the same coherent world, then authoring a scene ledger that encodes each of 4–8 chapters — camera endpoint, lighting/fog state, story beat, interaction targets, asset dependencies — as structured data rather than scattering magic numbers through CSS and the render loop.

The technical core is the scroll-to-state mapping: `scrollY` converts into a fractional chapter progress value kept in two forms — an exact value for navigation, URLs, and accessibility, and a separately smoothed value for camera and visual interpolation only — so the same scroll position always reproduces the same story state forward, backward, or after a reload. It covers cinematic camera authoring (composing every chapter endpoint at both desktop and mobile before interpolating between them with Catmull-Rom curves), a real PBR materials and lighting discipline, a concrete per-device performance budget (triangle counts, draw calls, DPR caps, frame-time targets), progressive loading with a real fallback poster, and a non-negotiable reduced-motion and WebGL-failure path that snaps to the nearest composed chapter and keeps the full DOM story readable regardless of whether the 3D layer works at all.

## Tips & Best Practices

- Write the world bible and scene ledger before touching Three.js code — retrofitting a coherent visual grammar onto a scene that's already grown ad hoc is far more expensive than defining it up front.
- Treat the exact-vs-smoothed scroll progress split as non-negotiable — using only a smoothed value for navigation and accessibility is exactly what breaks reload-at-depth and browser back/forward.
- Profile the performance budget table on an actual mid-range mobile device, not just a development machine — the mobile triangle/draw-call/DPR targets exist because desktop-tuned scenes routinely fail on real phones.

## Limitations

- A substantial commitment — the world bible, scene ledger, and full verification pass (camera endpoints across viewports, reduced motion, WebGL failure, hidden-tab resume) are appropriate for a flagship page, not a quick prototype.
- Assumes real-time 3D is the right choice for the project; the source material explicitly notes to evaluate real-time-3D versus pre-rendered-video first for simpler needs, since a rendered video sequence is dramatically cheaper to build and run.
- Performance budgets are starting envelopes tuned for typical scrollytelling scenes — a genuinely dense simulation or a VR-adjacent experience will need its own profiling pass rather than assuming these numbers hold.
